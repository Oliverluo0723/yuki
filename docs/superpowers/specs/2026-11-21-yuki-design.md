## 1. 這是什麼、為什麼做

一件握在手裡看的雪。作品是一個手機網頁：手機直立拿著，眼前是一層層排到遠處、正在落下的雪；把手機平放在掌心，雪就一片片落在玻璃上，停一下，化掉。

起點是使用者站在北海道的雪裡看雪落下的經驗。〔使用者〕他注意到的是「落下的方式」：北海道的雪又乾又輕，會飄、打轉、被風帶走；他站在雪裡面，視線在「平視（看整片）」和「低頭（看落在身上的那幾片）」之間來回。

為什麼這樣做：

- 〔使用者〕這一件要做的是**藝術**，不是工具（Oto）也不是遊戲（Block Flyer）。作品做出來是為了被體驗，本身就是終點。
- 〔使用者〕**只是在螢幕上畫出來太無聊**。人要進到雪裡。
- 〔使用者〕用 **p5.js** 來表達。

一句話：**手機怎麼拿，就是你怎麼看雪。**

## 2. 目標、非目標、反目標

### 目標

1. 〔使用者〕手機是觀看的方式：直立＝平視，平放在掌心＝低頭。
2. 〔使用者〕雪的主角是「落下」：遠近、飄、打轉、被風帶斜。
3. 〔使用者〕有一個**實際模式**，照北海道現在的天氣下雪。
4. 〔提議〕另有一個**常雪模式**，雪一直在下，條件由作品自己慢慢變化。這是預設模式。
5. 〔使用者〕靜態網站，部署在 GitHub Pages。
6. 〔使用者〕看得見的雪都由 p5.js 畫。
7. 〔提議〕不需要說明：把手機交給一個沒聽過這件作品的人，他在一分鐘內會自己發現「放平之後不一樣」。
8. 〔使用者〕在電腦上用滑鼠表達同一件事（見 5.7）。手機仍然是這件作品原本的樣子，電腦是它的翻譯。

### 非目標（第一版不做）

- ~~聲音~~：原本列為不做，使用者在實作完成後要求加入，見第 11 節。
- 鏡頭、手部或身體追蹤、投影。
- 匯出圖片或影片。
- 雪在地上或玻璃上越積越多。主題是落下，不是覆蓋。
- 指南針（讓風向跟著觀眾實際面對的方位）。
- 給觀眾用的設定面板。

### 反目標（做出來就算失敗）

- **看起來像螢幕保護程式或聖誕節特效**：一堆大小相近的白色圓點等速往下掉。
- **實際模式作假**：北海道沒下雪時畫面卻有雪。實際模式裡沒有就是沒有，絕不偷偷用模擬的雪補上。
- **需要看說明才會玩**。
- **介面蓋住雪**：按鈕、面板、常駐文字佔掉畫面。

## 3. 限制

- 靜態網站，沒有後端，沒有需要保密的金鑰。
- iPhone 要讀手機姿態，必須在使用者點擊之後呼叫 `DeviceOrientationEvent.requestPermission()`，而且網址必須是 https。所以一定有一個「點一下開始」的入口。Android Chrome 不需要請求權限，但同樣要 https。
- 手機不碰螢幕約 30 秒就會變暗、鎖定，而這件作品大部分時間不需要碰螢幕。開始後要用 Screen Wake Lock API 讓螢幕保持亮著，頁面回到前景時重新請求。
- 手機效能：目標是使用者自己的手機上穩定 60 fps，最低可接受 30 fps。雪片數量要能依實際幀率自動增減。
- 手機螢幕的像素密度常是 3，p5 預設會照這個密度開畫布，太重。`pixelDensity` 上限設 2。
- 天氣資料來自 Open-Meteo（見第 6 節）：免費、非商用、要標示來源。建置者動工前請到 open-meteo.com 確認目前的條款與署名寫法。

## 4. 考慮過的做法

### 4.1 p5 到底在畫雪的什麼

| 做法 | 得到 | 代價 |
|---|---|---|
| **畫深度**：雪有遠近、失焦、風場 | 最接近「站在裡面」 | 做不好就變回雪景特效 |
| **畫軌跡**：不畫雪片，畫它走過的路，像長時間曝光 | 「落下的方式」直接變成畫面，接上前作「痕跡是紀錄」的線 | 比較像看一張圖成形，「人在雪裡」的感覺弱 |
| **畫成版畫**：平塗、紙感、兩三種大小的白點 | 辨識度最高 | 是「雪的圖」，不是「在雪裡」 |

**採用：畫深度，把軌跡當成一個可調的數字。**〔提議〕使用者沒有明確選，話題直接轉到「不能只是畫在螢幕上」，所以照 Claude 的建議走：每片雪畫成一小段短線，短線留多久是一個參數，短就是站在雪裡，長就接近風的素描。最後停在哪個值，由使用者在手機上調著看決定。

### 4.2 人怎麼進到雪裡

| 做法 | 說明 |
|---|---|
| **手機就是你的手** | 直立平視、平放低頭、傾斜改變雪的方向 |
| 身體在雪裡 | 鏡頭當鏡子，雪落在輪廓上 |
| 雪落在真的空間 | 投影機，需要場地 |
| **北海道現在的雪** | 接即時天氣 |

**採用：手機＋北海道即時天氣。**〔使用者〕原話是「就 1 + 4」，並且說「實際的就是一個模式」。

### 4.3 怎麼蓋

| 做法 | 說明 |
|---|---|
| **A. Vite + pnpm + TypeScript + p5.js 2.x**（同 One Stroke） | 本機可開 https，手機連同一個 Wi-Fi 直接測；規則可寫測試 |
| B. 不打包，CDN 載入 p5（同 Hand Slit） | 最簡單，但每次在手機上測都要先推上 GitHub |

**採用：A。**〔使用者〕這件的手感全在「手機怎麼拿」，需要在手機上反覆試。

## 5. 觀眾會看到什麼

### 5.1 入口

打開網址，看到一個安靜的畫面：作品名稱、一句話、「點一下開始」。點下去時做三件事：請求讀取手機姿態的權限、請求螢幕保持亮著、進入作品。

- 權限被拒絕或裝置沒有感測器：照樣進入，停在平視，底部出現一行小字說明「這件作品要拿在手上看，請允許讀取手機的動作」（文字由建置者斟酌）。
- 入口也放資料來源署名（Open-Meteo）。

文字用繁體中文，越少越好。〔提議〕

### 5.2 姿態：一個從 0 到 1 的數字

從感測器算出「螢幕朝天的程度」，稱為 `posture`：0 是直立，1 是平放、螢幕朝上。經過平滑，不能抖。

```
  posture = 0（平視）       posture = 1（低頭）
  ┌───────────┐            ┌───────────┐
  │ .  ·  .  ·│            │           │
  │·  *   ·  *│            │    ❄      │
  │  ✻  ·  ✻  │            │        ·  │ ← 落在玻璃上
  │❄    ❄    ❄│            │  ❄        │   停住、化掉
  └───────────┘            └───────────┘
```

兩種看法之間是**連續過渡**，不是切換。大約在 0.35 到 0.65 之間，遠處的雪逐漸淡去，落在玻璃上的雪逐漸出現。確切的過渡畫面交給建置者，要求是：沒有硬切、沒有在臨界點閃爍、慢慢放平時每個中間角度看起來都合理。

螢幕朝下、或往後仰超過平放：當作 1 處理。

### 5.3 平視（直立）

整個畫面是雪，沒有地面、沒有景物。

- **遠近**：每片雪有自己的深度。遠的小、慢、淡、密；近的大、快；最近的幾片是失焦的模糊圓斑，偶爾從眼前掠過。
- **落下的方式**：每片雪有自己的飄動（左右擺、打轉的頻率和幅度都不同），不是直線等速。
- **風**：整片雪受同一個風影響，風由「基本風」加上一張隨時間流動的 `noise()` 場組成，所以會有一陣一陣、一塊一塊的變化。基本風從哪裡來見第 6 節。
- **雪朝真正的地面落**：〔提議〕雪落下的方向跟著真實的重力。把手機往左歪，雪在螢幕上就往左下斜。

  這一點修正了討論時說的「傾斜改變風」：實際模式的風必須來自北海道，手機的傾斜不能同時也是風，所以傾斜改變的是「下」的方向。在螢幕上看起來一樣（雪往低的那邊斜），而且兩個模式行為一致。
- **短線**：每片雪畫成從上一個位置到現在位置的一小段，長度由 `trail` 參數控制（0 是一個點）。

平視時觸碰螢幕或按滑鼠沒有作用（角落的模式標籤除外）。

### 5.4 低頭（平放）

畫面是一塊暗而乾淨的玻璃，雪一片一片落上來。

一片雪的一生：

1. **靠近**（約 1–2 秒）：先是一個大而淡、很模糊的影子，逐漸變小、變清楚，像從上方落向玻璃。
2. **落定**：停在玻璃上的某一點，成為一枚小小的六角結晶。每一枚形狀不同（用種子產生），用細線畫，大小約 20–40 px。〔提議〕
3. **停留**：幾秒。越冷停越久（溫度來源見第 6 節）。
4. **化掉**（約 1 秒）：結晶的枝縮回、糊成一小滴水，水滴淡去。

- 落下的頻率跟雪量成正比。
- 同時停在玻璃上的雪有上限（起始值 30 枚），永遠不會積滿。
- **手指是暖的**：手指碰到的地方，附近（起始值半徑 60 px）的雪立刻化掉；手指離開後那一塊還會暖 1–2 秒，新落上去的雪也化得快。

以上數字都是起始值，建置者和使用者在手機上調。

### 5.5 兩個模式

右下角有一行很小、很淡的文字，顯示現在的模式；點它切換。這是畫面上唯一的常駐介面。〔提議〕

| | 常雪模式（預設） | 實際模式 |
|---|---|---|
| 標籤 | 作品名稱或「雪」（建置者斟酌） | 地名、當地時間、氣溫，例：`旭川 14:45 −6°C` |
| 雪量 | 一直有雪，量慢慢起伏 | 照資料；沒下就沒有雪 |
| 風 | 作品自己慢慢變 | 照資料 |
| 冷暖 | 作品自己慢慢變 | 照資料 |
| 晝夜 | 照觀眾自己的當地時間 | 照北海道當地的晝夜 |

實際模式沒有雪時：畫面只有底色，標籤顯示地名、時間和「現在沒有下雪」。放平也一樣，玻璃上不會有雪。

預設是常雪模式的理由：第一次打開的人如果看到空畫面，會以為壞了。

### 5.6 晝夜

- **夜**：深色底，雪是亮的。
- **晝**：淺灰白的底，雪只比底色亮一點或暗一點，靠失焦和動態才看得出來。

以上說的是平視。**低頭時玻璃永遠是深色的**，白天也一樣，結晶永遠是亮的細線。〔提議〕理由：人低頭看雪，看的是落在深色袖子或手套上的那幾片，淺色的底上看不見結晶。白天的玻璃可以比夜裡淺一點（像日光下的深色外套），夜裡接近黑。所以白天把手機放平時，畫面會從亮轉暗，這個轉變交給 5.2 的過渡處理，它對應的是視線從明亮的天空落到自己的袖子上。

兩套配色都要做。確切顏色交給建置者，白天玻璃的深淺放進開發面板；可以參考 One Stroke 的 `src/color/nippon.ts`（日本傳統色）。

### 5.7 在電腦上

〔使用者〕電腦沒有感測器，改用滑鼠表達。對應方式是〔提議〕：

| 手機 | 電腦 |
|---|---|
| 把手機從直立慢慢放平 | **往下捲**（滾輪或觸控板）：`posture` 從 0 連續走到 1；往上捲回到平視 |
| 左右歪手機 | **滑鼠左右移動**：游標離畫面中央越遠，雪往那一邊斜得越多 |
| 手指碰玻璃 | **游標本身就是手指**：低頭時，游標附近的雪會化掉，不需要按下 |

- 選「捲動」而不是「滑鼠上下移動」來控制抬頭低頭，是因為低頭時游標要能在整塊玻璃上自由移動去融雪；如果上下位置已經被用來決定姿態，游標就被綁住了。
- 頁面本身不捲動，滾輪事件只用來改 `posture`。
- 入口畫面在電腦上多一行小字：這件作品原本是拿在手上看的，並附上網址；另外提示「移動滑鼠，往下捲」。進入作品後不再有提示。
- 判斷用哪一種輸入：拿到感測器資料就用感測器；沒有就用滑鼠。手機上權限被拒絕時，不提供替代的觸控操作（第一版），維持 5.1 的處理。

### 5.8 開發用面板

網址加上 `?dev` 時出現 lil-gui 面板（同 One Stroke），可以直接調：`posture`、左右傾斜、雪量、風、冷暖、晝夜、`trail`、雪片數量、模式。用來在電腦上固定某個姿態或天氣條件、精確調整數值。這個面板不給觀眾用。

## 6. 天氣

### 6.1 資料來源

Open-Meteo，免帳號、免金鑰，瀏覽器可直接呼叫。2026-11-21 實測可用：

```
https://api.open-meteo.com/v1/forecast
  ?latitude=43.06&longitude=141.35
  &current=temperature_2m,snowfall,weather_code,wind_speed_10m,wind_direction_10m,wind_gusts_10m,is_day
  &timezone=Asia/Tokyo
```

實測回應（札幌，當地 14:45）：`snowfall` 0 cm、`temperature_2m` 1.3 °C、`wind_speed_10m` 7.7 km/h、`wind_direction_10m` 336°、`wind_gusts_10m` 19.1 km/h、`weather_code` 1、`interval` 900 秒。`is_day` 後來也實測過，回傳 `0` 或 `1`。

要知道的三件事：

- 資料每 15 分鐘更新一次。它給的是天氣條件，不是每一片雪；雪片仍然是 p5 模擬的。
- 數字是氣象模型對那一格區域的估算，不是街角的感測器。
- `wind_direction_10m` 是風**吹來**的方向。

### 6.2 看哪裡

〔提議〕設定檔裡放一份北海道地點清單（名稱、經緯度），起始內容：札幌、旭川、小樽、俱知安、富良野、函館、稚內、釧路、帶廣、網走。實際模式顯示其中**現在雪下得最大**的那一個，並在標籤寫出地名；全部都沒下，就顯示清單第一個地點和「現在沒有下雪」。

使用者可以把清單改成只剩一個地點（例如他當時站的地方），程式不用改。

Open-Meteo 可以用逗號一次查多個座標（已實測）：多個座標回傳陣列，順序同請求；單一座標回傳物件。

「正在下雪」的判定：`snowfall > 0`，或 `weather_code` 屬於 71、73、75、77、85、86。

〔提議〕很輕的乾雪在 15 分鐘的讀數裡可能是 0 cm，但天氣代碼仍然說在下雪，而那正是這件作品要的雪。所以**代碼說下雪就算下雪**：資料來源自己說在下，畫出來不算作假。

- 代碼給 `amount` 一個下限：71、77、85（小雪）是看得出來的最小值；73（中雪）約一半；75、86（大雪）偏高。`amount` 取「由 `snowfall` 算出的值」和「代碼下限」兩者較大的那個。
- 選「雪下得最大」的地點：先比 `snowfall`，相同再比代碼的強度，再相同就照清單順序。

### 6.3 天氣怎麼變成雪

兩個模式都產生同一種資料，之後所有程式只讀它，不知道它來自哪個模式：

```ts
interface SnowConditions {
  amount: number;   // 0–1，雪量。0 = 沒有雪
  windX: number;    // 橫向的風，負值往左、正值往右
  gust: number;     // 0–1，風忽強忽弱的程度
  wetness: number;  // 0–1，0 = 又乾又輕，1 = 又濕又重
  isDay: boolean;
}
```

換算的起始規則（都要在手機上用眼睛調，換算本身要有測試）：

- **amount**：沒在下雪（見 6.2 的判定）時為 0；在下雪時至少有一個看得出來的最小值，之後隨降雪量增加，逐漸趨緩到 1（每 15 分鐘約 1 cm 以上視為最大）。`snowfall` 是 0 但代碼說下雪時，用 6.2 的代碼下限。
- **windX**：假設觀眾面向正北，所以西風從畫面左邊吹向右邊。取風向在東西方向的分量乘上風速。真實的 10 m 風速直接換算會讓雪幾乎橫著飛，所以要壓縮：0 km/h 不斜，20 km/h 約斜 45°，上限約 70°。
- **gust**：陣風與平均風速差得越多，值越高。
- **wetness**：−5 °C 以下為 0，0 °C 以上為 1，中間線性。乾的雪片小、落得慢、飄得多；濕的大、落得快、比較直。它也決定雪在玻璃上停多久。
- **isDay**：直接用資料。

常雪模式：`amount`、`windX`、`gust`、`wetness` 各自沿著很慢的 `noise()` 曲線變化（幾分鐘一個起伏），`amount` 永遠不低於一個看得出來的最小值；`isDay` 用觀眾裝置的當地時間（6:00–18:00 為晝，建置者可改用更好的判斷）。

### 6.4 更新與失敗

- 進入實際模式時抓一次，之後在實際模式且頁面可見時每 15 分鐘抓一次。
- 條件改變時，雪要用幾秒鐘漸變過去，不能跳。
- 抓不到：一小時內的舊資料繼續用；沒有或太舊，畫面沒有雪，標籤顯示「讀不到北海道的天氣」。**不可以改用模擬的雪**。

## 7. 怎麼蓋

### 7.1 工具

沿用 One Stroke 的設定（可直接參考 `/Users/bd/Desktop/work/One Stroke/` 的 `vite.config.ts`、`tsconfig.json`、`biome.json`、`.github/workflows/pages.yml`）：

- Vite + pnpm + TypeScript（`strict`）
- p5.js 2.x，instance mode
- Biome、Vitest
- lil-gui（只用在開發面板）
- GitHub Actions 部署到 GitHub Pages，build 帶 `--base=/<repo 名>/`

〔提議〕新增一項：開發伺服器開 https 並對區域網路開放（例如 `@vitejs/plugin-basic-ssl` 加 `server.host: true`），手機連同一個 Wi-Fi、接受自簽憑證的警告後就能測。

〔提議〕畫面先用 p5 的 2D 畫布。模糊的雪片不要每一格用濾鏡算，預先畫成幾張不同模糊程度的小圖再貼。手機上跑不動時，建置者可以改用 WEBGL 模式，但看得見的雪仍然要由 p5 畫。

### 7.2 p5 的範圍

p5 只負責畫。感測器、權限、螢幕常亮、天氣、觸控都用瀏覽器原生的介面，各自放在獨立的模組，不透過 p5 的包裝。這樣這些模組不依賴畫面，可以單獨測試。

### 7.3 手機姿態

- 由 `deviceorientation` 事件的 `beta`、`gamma` 推出重力在螢幕座標裡的方向，再得到 `posture`（螢幕朝天的程度）和螢幕平面內「下」的方向。
- 不建議用 `devicemotion` 的 `accelerationIncludingGravity`：iOS 和 Android 的正負號相反。
- 要把螢幕自動旋轉算進去（`screen.orientation.angle`）：手機轉成橫向時畫布重排，雪仍然朝真正的地面落。
- 平滑可以參考 One Stroke 的 `src/input/oneEuro.ts`。
- 感測器和滑鼠都翻譯成同一種資料（`posture`、螢幕平面內「下」的方向、暖的位置），之後的程式只讀這份資料，不知道它來自手機還是滑鼠。這跟 Hand Slit 把手、滑鼠、觸控都翻譯成「掃描線兩個端點」是同一個做法。

### 7.4 建議的模組劃分

建置者可以調整，但這幾條界線要守住：姿態、天氣、雪的狀態、畫，四者互不知道對方的內部。

  input/touch.ts          觸控點 → 玻璃上的暖區
  input/wakeLock.ts       螢幕常亮

### 7.5 測試

Vitest 只測不用看畫面就能判斷對錯的部分：

- 姿態角度 → `posture` 與「下」的方向（含螢幕旋轉）
- 滑鼠的捲動與位置 → 同一種姿態資料
- 天氣資料 → `SnowConditions`（含沒下雪、極端值、缺欄位）
- 選出雪下得最大的地點
- 雪片的更新（深度與大小速度的關係、飄出邊界後回到另一邊）
- 玻璃上的雪的一生（靠近、落定、停留、化掉、被手指碰到）
- 抓天氣失敗時的處理

畫面和手感由使用者在自己的手機上判斷。

### 7.6 聲音的接點

第一版沒有聲音。但 `snow/landing.ts` 要對外發出事件（落定、化掉、被手指融化），`SnowConditions` 也是公開的，之後要加聲音只需要訂閱這些，不用改雪的程式。

## 11. 追加：聲音（2026-11-21）

〔使用者〕原話是「加個下雪會有的聲音」。以下做法是〔提議〕：使用者沒有逐項確認，只表示在等聲音，所以照提議先做，由使用者用耳朵聽了再調。

### 做什麼

下雪時真正聽得到的聲音很少，做三層，全部用 Web Audio 合成，沒有音檔：

| 聲音 | 什麼時候 | 跟著什麼變 |
|---|---|---|
| 悶住的安靜：很低、很輕的空氣聲 | 一直都在 | 雪越大越悶 |
| 風：一陣一陣的低鳴 | 平視時明顯，低頭時退到遠處 | 風的強弱和陣風（不看方向）；實際模式就是北海道現在的風 |
| 雪落下的細碎聲：極輕的「沙、嗒」 | 平視時是稀疏的一片；低頭時每一片落在玻璃上各響一下，左右對應畫面位置 | 雪量；乾雪清脆、濕雪悶 |

手指（或游標）把雪融掉時是一聲很短的氣音。

### 規則

- 實際模式沒下雪時沒有雪的聲音，但風還在，因為風是真的資料。讀不到天氣時只剩空氣聲和最低限度的風。這跟反目標一致：雪的聲音只來自雪量。
- 聲音在入口那一下點擊裡開始（瀏覽器規定），兩秒淡入；分頁切到背景時暫停。
- 不加靜音按鈕：音量由裝置的音量鍵控制，畫面維持只有右下角那一行字。開發面板有 `volume` 可調。
- 作品沒有聲音時也必須成立：iPhone 切到靜音模式時，網頁的聲音會被靜音。

### 考慮過的做法

- **程式合成（採用）**：不用找素材、沒有授權問題，能連續地跟著風和雪量變。代價是風聲不如實地錄音豐富。
- 錄音素材：比較真實，但要找可公開散布的素材，而且很難連續地跟著條件變化。之後想換可以再換。

### 怎麼蓋

- `src/sound/params.ts`：雪的條件與姿態 → 聲音參數（純函式，有測試）。
- `src/sound/engine.ts`：Web Audio 的接線。一段循環的白噪音分別經過低通（空氣）、帶通（風）、窄帶通（風大時的哨音）；細碎聲是很短的噪音顆粒。最後過一個限幅器。
- 玻璃上的聲音訂閱 `Landings.on()` 的事件（7.6 留的接點）。

### 沒辦法由程式確認的事

好不好聽、像不像雪，只能用耳朵判斷。程式能確認的只有：聲音確實在播、參數有跟著條件變、音量調到 0 會靜音。
